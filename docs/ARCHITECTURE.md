# Архитектура web-gradebook

Документ фиксирует то, что уже реализовано на этапе 1, и то, как этапы 2–3 (Supabase и Google Drive)
встраиваются без переделки домена и UI.

---

## 1. Общая картина

```
                    ┌──────────────────────────────────────────────┐
                    │ React UI (mobile-first, роутер HashRouter)   │
                    │ экраны читают данные через useLiveQuery      │
                    └───────────────┬──────────────────────────────┘
                                    │ read / write
                    ┌───────────────▼──────────────────────────────┐
                    │ Dexie (IndexedDB) — источник истины для UI    │
                    │ subjects / groups / subgroups / students /    │
                    │ enrollments / activities / sessions /        │
                    │ grades / attendance                           │
                    └───────┬──────────────────────────┬───────────┘
                            │ этап 2                   │ этап 3
                    ┌───────▼─────────┐        ┌───────▼───────────┐
                    │ mutation queue  │        │ debounce push     │
                    │ → Supabase      │        │ → drivestash      │
                    │   (Realtime +   │        │   (Google Drive,  │
                    │    pull/push)   │        │    appDataFolder) │
                    └───────┬─────────┘        └───────┬───────────┘
                            │                          │
                    ┌───────▼─────────┐        ┌───────▼───────────┐
                    │ Postgres + RLS  │        │ 9 JSON-файлов     │
                    │ auth.uid()=user │        │ (по типу записей) │
                    └─────────────────┘        └───────────────────┘
```

Ключевые инварианты:

1. UI никогда не ждёт сеть: все чтения и записи идут в Dexie.
2. У каждой записи есть `createdAt`, `updatedAt`, `deletedAt`; физических удалений из приложения нет.
3. Supabase — основной канал меж устройств (LWW по `updatedAt`).
4. Google Drive (`drivestash`) — только страховка от потери IndexedDB, не канал синхронизации:
   файл целиком перезаписывается, конфликт разрешается на уровне файла.
5. Supabase-аккаунт (Яндекс ID) и Google-аккаунт для бэкапа — два независимых OAuth-потока.

## 2. Локальная схема Dexie (v2)

Файл `src/db/db.ts`. Дата-модель — `src/db/types.ts`.

| Стор | Индексы | Назначение |
| :--- | :--- | :--- |
| `subjects` | `id, name, archivedAt, updatedAt` | предметы, шкала, веса видов занятий |
| `groups` | `id, name, updatedAt` | группы («4232») |
| `groupMembers` | `id, groupId, studentId, [groupId+studentId], updatedAt` | состав группы, не зависящий от предмета (v2) |
| `subgroups` | `id, subjectId, groupId, [subjectId+groupId], updatedAt` | подгруппы (только лабораторные) |
| `students` | `id, name, updatedAt` | глобальная база студентов |
| `enrollments` | `id, subjectId, studentId, groupId, [subjectId+groupId], [subjectId+studentId], subgroupId` | студент × предмет × группа × подгруппа |
| `activities` | `id, subjectId, type, [subjectId+order]` | занятия: лекция/практика/лабораторная |
| `sessions` | `id, subjectId, activityId, groupId, subgroupId, date, [activityId+date], [subjectId+date]` | проведения занятия по датам |
| `grades` | `id, subjectId, activityId, sessionId, studentId, [sessionId+studentId], [subjectId+studentId]` | баллы (привязаны к сессии) |
| `attendance` | `id, subjectId, sessionId, studentId, [sessionId+studentId]` | явка на сессии |

### Маппинг на Supabase

Имена полей — прямой camelCase → snake_case, массивы/объекты → `text[]`/`jsonb`.

| Dexie | Supabase | Примечание |
| :--- | :--- | :--- |
| `Subject.typeWeights` | `subjects.type_weights jsonb` | `{lecture, practice, lab}` |
| `Subject.enabledTypes` | `subjects.enabled_types text[]` | |
| `Subject.archivedAt` | `subjects.archived_at` | архив ≠ soft-delete |
| `Activity.order` | `activities.order_index` | `order` — зарезервированное слово SQL |
| `Activity.maxScore` | `activities.max_score` | `0` = наследовать шкалу предмета |
| `Activity.autoRotate` | `activities.auto_rotate` | |
| `ActivitySession.date` | `activity_sessions.date` | локальная дата `YYYY-MM-DD` |
| `Student.id` | `students.id` | студент глобальный, баллы раздельные |
| `AppSettings` | не синхронизируется | тема и PIN локальны |

Серверная схема, индексы, RLS и триггеры — `supabase/schema.sql`.

### Локальные настройки

`AppSettings` (тема, PIN-хеш, автоблокировка, последний предмет) намеренно **не** хранится в Supabase
и **не** попадает в JSON-бэкап: PIN — секрет устройства, тема — предпочтение устройства.
Хранится в `localStorage` (`web-gradebook:settings`), PIN — SHA-256 от `salt:pin`.

## 3. Схема `drivestash` (этап 3)

`drivestash` хранит **все записи одного типа в одном JSON-файле** в скрытой папке
`appDataFolder` Google Диска. Имя файла = имя стора с префиксом проекта:

```
web-gradebook:subjects
web-gradebook:groups
web-gradebook:subgroups
web-gradebook:students
web-gradebook:enrollments
web-gradebook:activities
web-gradebook:sessions
web-gradebook:grades
web-gradebook:attendance
```

Структура файла:

```jsonc
{
  "format": "web-gradebook-store",
  "version": 1,
  "store": "web-gradebook:grades",
  "updatedAt": "2026-03-01T10:00:00.000Z",
  "records": [
    {
      "id": "…uuid…",
      "createdAt": "2026-02-01T09:00:00.000Z",
      "updatedAt": "2026-03-01T09:59:00.000Z",
      "deletedAt": null,
      "subjectId": "…",
      "activityId": "…",
      "sessionId": "…",
      "studentId": "…",
      "score": 87,
      "comment": ""
    }
  ]
}
```

`SyncRecord` — это запись предметной сущности как есть (те же поля, что в Dexie), а не обёртка
`{id, data}`: так проще восстановление и отладка. Инварианты — `id` и `updatedAt` обязательны,
`deletedAt` — tombstone.

### Push

1. Любой `put`/`delete` в Dexie ставит стор в очередь «грязных».
2. Дебаунс 1.5–2 с на стор, затем читается весь текущий стор из Dexie.
3. Файл собирается целиком (`records` отсортированы по `id`), сжимается DEFLATE
   (`new CompressionStream('deflate-raw')`) и пишется поверх файла в `appDataFolder`.
4. Параллельные push одного стора сериализуются; последний выигрывает (LWW на уровне файла),
   поэтому при конфликте двух устройств побеждает тот, кто записал позже.

### Restore

1. Прочитать все 9 файлов, распаковать `DecompressionStream('deflate-raw')`.
2. Для каждой записи: если локальной нет или локальная `updatedAt` старее — записать.
3. Показать сводку и предложить полный JSON-бэкап перед восстановлением.

### Статус

`idle | syncing | synced | offline | error` — индикатор в хедере/настройках, ошибки не блокируют
работу: данные уже в IndexedDB.

## 4. Синхронизация Supabase (этап 2)

### Очередь мутаций

Локальный стор `syncQueue` (Dexie v2, добавляется на этапе 2):

```ts
interface Mutation {
  seq: number;          // autoincrement
  store: StoreName;     // subjects | … | attendance
  recordId: string;
  updatedAt: string;
  createdAt: string;    // попытка, для backoff
}
```

Все мутации из `src/db/repo.ts` уже пишут `updatedAt` — на этапе 2 к ним добавляется постановка
в очередь в той же транзакции Dexie.

### Push

1. Триггеры: `online`, `visibilitychange → visible`, интервал 30 с, после каждой мутации (дебаунс 1 с).
2. Пачка до 200 мутаций: сгруппировать по сторам, прочитать актуальные записи из Dexie.
3. `upsert` в Supabase (`on conflict (id) do update`) с `updated_at` из записи.
4. Успех — удалить мутации из очереди; ошибка — экспоненциальный backoff (1, 2, 4 … 60 с),
   ошибки авторизации останавливают движок до перелогина.

### Pull

1. Хранится `lastPulledAt` (ISO) в `syncMeta`.
2. Для каждого стора: `select * where updated_at > lastPulledAt order by updated_at asc limit 500`
   (пагинация по `updated_at`, `id`).
3. Применение — LWW по `updatedAt`: локально более новая запись не перетирается, но её мутация
   останется в очереди и уйдёт на сервер следующим push.
4. Tombstone (`deleted_at`) применяется как soft-delete локально.
5. Realtime-подписка (`postgres_changes`) — опциональное ускорение; корректность обеспечивает pull.

### Конфликты и порядок

- LWW по `updatedAt` (UTC ISO с миллисекундами).
- Часы устройств могут расходиться: при расхождении > 2 минут показывается предупреждение
  в настройках синхронизации; серверный `updated_at` из триггера используется как арбитр
  при равных клиентских значениях.
- Ссылочная целостность: push идёт в порядке `subjects → groups → subgroups → students →
  enrollments → activities → sessions → grades → attendance`; pull — в обратном для удалений
  не требуется (soft-delete), но порядок применения тот же.

### Keep-alive

Бесплатный проект Supabase засыпает после недели простоя. Workflow
`.github/workflows/supabase-keepalive.yml` раз в сутки делает лёгкий `GET /rest/v1/` c anon-ключом.
Альтернатива — внешний cron. Секреты: `SUPABASE_URL`, `SUPABASE_ANON_KEY`.

## 5. OAuth-потоки

### 5.1 Яндекс ID для Supabase (PKCE)

Требование ТЗ: вход в Supabase через Яндекс ID. Важное ограничение: **в hosted Supabase нельзя
зарегистрировать произвольного OAuth-провайдера**, а Яндекс ID — OAuth2 без OIDC-дискавери.
Поэтому предлагается брокер на Supabase Edge Function, который остаётся в бесплатном тарифе
и не требует self-hosted GoTrue.

```
Браузер                    Edge Function (Deno)                  Яндекс / Supabase Auth
   │  GET /authorize          │                                        │
   ├─────────────────────────►│  state + PKCE verifier (в БД/подпись)  │
   │  302 на oauth.yandex.ru  │                                        │
   │◄─────────────────────────┤                                        │
   │  code + state            │                                        │
   ├─────────────────────────►│  POST /token (code_verifier) ─────────►│
   │                          │◄──────── access_token ────────────────┤
   │                          │  GET login.yandex.ru/info ────────────►│
   │                          │◄──────── id, email, name ─────────────┤
   │                          │  admin.createUser (service role)       │
   │                          │  admin.generateLink(magiclink)         │
   │  302 /#/auth?token_hash  │                                        │
   │◄─────────────────────────┤                                        │
   │  supabase.auth.verifyOtp({ token_hash, type: 'magiclink' })      │
   ├──────────────────────────────────────────────────────────────────►│
   │◄──────────────────────── session (access + refresh) ─────────────┤
```

Параметры Яндекс OAuth:

- Client ID — `VITE_YANDEX_CLIENT_ID` в приложении и `YANDEX_CLIENT_ID` в секретах функции;
- Redirect URI — `https://<project-ref>.supabase.co/functions/v1/yandex-oauth/callback`;
- PKCE включён (S256), scope `login:email login:info`;
- токен Яндекса **не сохраняется** — используется только для получения профиля.

Защита: `state` одноразовый, TTL 10 минут, хранится в таблице `oauth_states` с RLS «только service
role»; service role key есть только у функции; после `verifyOtp` клиент получает обычную сессию
Supabase, и все запросы к таблицам идут под RLS `auth.uid() = user_id`.

Альтернатива, если появится свой хостинг: GoTrue с `GOTRUE_EXTERNAL_YANDEX_*` (в hosted-тарифе
недоступно). Скелет функции — `supabase/functions/yandex-oauth/index.ts`; решение зафиксировано в
`docs/DECISIONS.md`.

### 5.2 Google Identity Services для `drivestash` (этап 3)

Отдельный поток, не связанный с Supabase:

- `VITE_GOOGLE_CLIENT_ID`, scope `https://www.googleapis.com/auth/drive.appdata`;
- Authorized JavaScript origins: `https://ezy4me.github.io`;
- `google.accounts.oauth2.initTokenClient({ client_id, scope, callback })`,
  `requestAccessToken({ prompt: '' })` для тихого обновления;
- access token живёт ~1 час, хранится в IndexedDB/памяти с `expiresAt`, refresh-token в браузере
  не используется; по истечении — повторный `requestAccessToken`;
- кнопка «Подключить Google Drive» в настройках, отключение — удаление токена;
- при `error`/`offline` бэкап просто откладывается, UI показывает статус.

## 6. Экраны и маршруты

`HashRouter` — чтобы GitHub Pages корректно отдавал deep links без 404.

| Маршрут | Экран | Содержимое |
| :--- | :--- | :--- |
| `/` | Предметы | активные/архив (фильтры появляются при необходимости), поиск, создание, демо-данные |
| `/groups` | Группы | список групп: студенты, предметы, средний балл и оценка |
| `/groups/:id` | Группа | состав с номерами, предметы с оценками, добавление студентов, зачисление на предметы; тап по студенту → профиль |
| `/students/:id` | Студент | все предметы, средний балл, посещаемость, работы по видам с предметом и цветом |
| `/stats` | Статистика | предмет × группа, распределение, рейтинг, отстающие |
| `/data` | Данные | перенос бэкапа, импорт расписания и студентов, очистка |
| `/settings` | Настройки | тема, PIN и автоблокировка, о приложении; вход в «Данные» |
| `/subject/:id` | Предмет | группы-бейджи, табы «Журнал / Таблица / Студенты / Сводка», настройки предмета; `?group=` preselected |
| `/activity/:id` | Занятие | сессии по датам, добавление сессий, дедлайн, веса |
| `/session/:id` | Выставление | вся группа с цветовым кодом подгрупп, номера, явка, баллы (для лекций — только явка); «Отметить всех» с отменой |
| `/subject/:id/student/:id` | Студент | итог, разбивка, динамика, работы, заметки |

Нижняя навигация: **Предметы, Группы, Статистика, Настройки**. «Данные» открываются из настроек.
Навигация видна на всех маршрутах; детальные экраны подсвечивают свой раздел.

### 6.1 Рабочий поток

```
Группы → группа → предмет → вид занятия → сессия → балл
Предметы → предмет → группа (бейдж) → вид занятия → сессия → балл
```

Группа — самостоятельная сущность: студенты добавляются один раз, `groupMembers` хранит состав,
а зачисление в предмет создаёт `enrollments` для всех участников и подгруппы по кругу.

### 6.2 Таблица журнала (`src/components/JournalTable.tsx`)

- отдельная таблица на каждый вид занятий (лабораторные / практики / лекции);
  вид без сессий не показывается, переключение — вкладками;
- строки — `groupRanking` группы по алфавиту; номер и цвет подгруппы;
- колонка — занятие, под ней подколонки с датами подгрупп (для лекций/практик — одна дата);
- клетка применяется только к студенту своей подгруппы, разделена на явку и балл;
- явка и балл сохраняются через `setAttendance` / `setGrade` сразу;
- `<thead>` (две строки), первая колонка и `<tfoot>` липкие; контейнер ограничен по высоте;
- снизу — посещаемость и средний процент колонки, справа — итог по виду занятий.

На desktop `--container-app` расширяется до 980 px, поэтому таблица показывает больше колонок;
на телефоне она прокручивается внутри, не создавая горизонтальный скролл страницы.

Группа выбирается в шапке экрана предмета и влияет на журнал, список студентов и сводку.
Вид занятия — вкладки внутри журнала (лекции / практики / лабораторные). На экране выставления
показывается вся группа: активная подгруппа редактируется, остальные видны для контекста
с их датой и баллом из собственной сессии.

### 6.2 Безопасность массовых действий

«Отметить всех присутствующими» и «поставить максимум» не находятся на основном экране.
Они живут в меню «…» и требуют подтверждения с количеством студентов и баллом — чтобы
случайное нажатие на паре не переписало весь журнал.

## 7. Домен

### 7.1 Расчёт итога (`src/domain/grading.ts`)

Для каждого студента и предмета строится набор «ячеек» — сессий, которые к нему относятся:

- лабораторные — только сессии его подгруппы;
- лекции и практики — все сессии его группы.

Для каждой ячейки: `w` — вес занятия (`activity.weight ?? subject.typeWeights[type]`),
`m` — максимум (`activity.maxScore || subject.scaleMax`), `s` — балл или 0.

```
finalPercent = Σ (w × s / m) / Σ w × 100     // пропуски = 0, это итоговая оценка
averagePercent = Σ (w × s / m) / Σ w × 100   // только по выставленным оценкам
completion = выставленные / ожидаемые × 100
```

**Лекции в формулу не входят.** `activityWeight` возвращает 0 для типа `lecture`, ячейки лекций
исключаются из `finalPercent`/`averagePercent`/`completion`, а посещаемость считается отдельно
(`lecturePresent`, `lectureSessions`). На экране сессии лекция не показывает поля балла.

Порог «сдал» — `subject.passThreshold` (по умолчанию 51%). Проценты дополнительно переводятся в
2–5: `0–50 → 2`, `51–70 → 3`, `71–85 → 4`, `86–100 → 5`; цвета заданы в `src/lib/grades.ts` и
используются в журнале, итоге студента, статистике и на карточках предметов. Для предметов
«сдал / не сдал» цвет определяется порогом.

### 7.2 Расписание и дедлайны (`src/domain/schedule.ts`)

- `planSessions` — генерация сессий: для лабораторных подгруппы чередуются по индексу
  (`1 → 2 → 1 → 2…`), для лекций/практик — одна сессия на всю группу.
- `resolveDeadline` — приоритет: дедлайн сессии → дедлайн занятия → дата следующего занятия
  этой же группы (для лабораторных — этой же подгруппы).
- `activityDeadline` — дедлайн последней сессии занятия.
- `studentActivityRows` (`src/domain/studentWorks.ts`) — ровно одна строка на занятие: только
  занятия с сессией этой группы, для лабораторных — сессия подгруппы. Это убирает дубли работ.

### 7.3 Импорт расписания (`src/db/scheduleImport.ts`)

Принимает плоский JSON проекта `web-schedule`: массив пар с `dates` (`ДД.ММ`), `group`
(может быть несколько через запятую), `type` (`лек` / `пр` / `л.р.`), `subject`, `time`.
Доступен импорт файла, вставка JSON в текстовое поле и скачивание примера
(`public/examples/schedule.json`).

- год выводится из выбранного начала учебного года: август–декабрь — этот год, январь–июль —
  следующий;
- каждая дата становится отдельным занятием с одной сессией, поэтому журнал повторяет сетку пар;
  **лабораторные объединяются в блоки по числу подгрупп**: две даты → одна «Лабораторная 1»
  с сессиями для подгрупп 1 и 2, а не две отдельные ЛР;
- нумерация занятий — в пределах предмета, группы и вида;
- **все группы из расписания создаются сразу** и видны в бейджах предмета; студенты добавляются
  отдельно — в расписании их нет;
- лабораторные получают две подгруппы и чередование `1 → 2` по датам;
- импортированные лекции сразу работают в режиме «только посещаемость»;
- повторный импорт пропускает пары, у которых уже есть сессия того же вида в тот же день.

Импорт выполняется одной транзакцией Dexie, предпросмотр показывает предметы, группы, количество
занятий и диапазон дат. Полный бэкап и пример для заполнения — в разделе «Данные»: пример
`public/examples/backup.json` содержит все сущности v2 и сразу проходит `parseBackup`.

### 7.4 Импорт студентов (`src/db/studentsImport.ts`)

Принимает сгруппированный формат
`{ subjects: [...], groups: [{ name, students: [{ name, subgroup }] }] }` или плоский список
`[{ name, group, subgroup, subjects }]`. Старый вариант с одним `subject` поддерживается.

- группа — самостоятельная сущность: студент сначала попадает в `groupMembers`;
- `subjects` необязателен; если указан, студенты сразу зачисляются в каждый предмет;
- группы находятся или создаются; подгруппы создаются до максимального индекса (минимум две);
- студенты ищутся по имени и переиспользуются, новые создаются;
- если группа уже зачислена в другие предметы, новый студент автоматически попадает и туда;
- оценки, сессии и посещаемость не затрагиваются;
- импорт идёт одной транзакцией, предпросмотр показывает группы, студентов и предметы.

## 8. Безопасность и приватность

- RLS на всех таблицах: `auth.uid() = user_id`; политики в `supabase/schema.sql`.
- PIN: 4–8 цифр, SHA-256 с солью, автоблокировка после простоя (по умолчанию 5 минут).
- Локальная база **не шифруется** (осознанное решение ТЗ): защита — PIN + RLS + HTTPS.
- Ключи: только `VITE_*` публичные значения (anon key, client id). Service role — исключительно
  в секретах Edge Function.
- В бэкап не попадают PIN и настройки темы.
- Google-токен не даёт доступа к остальному Диску: `drive.appdata` видит только `appDataFolder`.
