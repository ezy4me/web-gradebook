# PROJECT_SPEC.md

# PWA «web-gradebook» — Итоговое техническое задание

> Название: **web-gradebook**.
> Репозиторий: `ezy4me/web-gradebook` (GitHub).
> GitHub Pages: `https://ezy4me.github.io/web-gradebook/`.
> `base` в Vite: `/web-gradebook/`.

## 1. Обзор

Прогрессивное веб-приложение (PWA) для преподавателя, который ведёт несколько предметов и выставляет студентам баллы за различные виды занятий. Приложение работает **офлайн-первым**, хранит данные локально в IndexedDB, синхронизируется между устройствами через **Supabase** и делает автоматический бэкап на **Google Drive** (скрытая папка `appDataFolder`). Разворачивается на **GitHub Pages**.

**Ключевые свойства:**
- Работает без интернета (Local-First).
- Синхронизация между устройствами через Supabase.
- Автоматический бэкап на Google Drive (защита от потери IndexedDB).
- Защита данных: RLS в Supabase + локальный PIN на устройстве.
- Mobile-first интерфейс, две темы (тёмная/светлая).
- Бесплатные тарифы Supabase, Google Drive API и GitHub Pages.
- Интерфейс — русский язык.
- **Авторизация в Supabase — через Яндекс ID** (кастомный OAuth-провайдер).

## 2. Функциональные требования

### 2.1. Предметы (курсы)
- Создание, переименование, архивирование, переключение между предметами.
- Набор **видов занятий**: лекции, практики, лабораторные. Практики и лекции можно отключать для предмета.
- **Гибкая шкала оценивания**: по умолчанию 0–100, редактируемая (0–10, зачёт/незачёт). Задаётся на уровне предмета и может переопределяться на уровне вида занятия.
- Списки занятий внутри предмета («Лаба 1», «Практика 3»), у каждого — максимальный балл и опциональный вес.
- **Расписание подгрупп для лабораторных**: по умолчанию подгруппы чередуются `1 → 2 → 1 → 2…` по датам. Правило применяется **только к лабораторным**; каждую дату сессии можно переопределить вручную.
- Для лекций и практик правило чередования не применяется — у них одна сессия на всю группу.

### 2.2. Студенты, группы, подгруппы
- Студенты — глобальная сущность (один студент может быть в нескольких предметах, баллы раздельные).
- Деление на **группы** (например, «ПИ-21»).
- **Подгруппы** используются **только для лабораторных занятий**. Лекции и практики проводятся для всей группы целиком; деления на подгруппы для них нет.
- Один студент может быть в разных группах в разных предметах.
- Размер группы ~20–25 человек, всего — пара сотен. Нужен поиск и фильтры.

### 2.3. Выставление баллов и посещаемости
- Экран «быстрого выставления» открывается **для конкретной сессии занятия** (занятие + дата, для лабораторных — ещё и подгруппа).
- Список студентов:
  - для **лабораторной** — только студенты выбранной подгруппы;
  - для **лекции/практики** — вся группа.
- **Посещаемость**: отдельная отметка «был / не был» для каждого студента на сессии. Режим «Отметить всех присутствующими» одной кнопкой.
- **Баллы**: поле для ввода балла (если применимо). Валидация: балл не превышает максимум для занятия.
- Кнопка **«Отметить всех»**: проставить максимум всем с последующей корректировкой.
- **Комментарий** к оценке и к студенту.

### 2.4. Итоговая оценка и формула расчёта
- Итоговая оценка рассчитывается **по сумме набранных баллов** с учётом весов занятий.
- Если по предмету используется смешанная система (**баллы + «сдал/не сдал»**), итог считается по формуле, где **лабораторные имеют больший вес**.
- **Пример**: 1 лаба = 100 баллов (вес 1.0), 1 практика = 100 баллов (вес 1.0). Если сдано 2 практики и 1 лаба, итог = (100 + 50) / 200 = 75%. Лабораторные работы значимее: при равном количестве занятий их вклад в итоговую сумму выше.
- Веса занятий настраиваются на уровне предмета. По умолчанию: лабораторные — вес 2, практики — вес 1, лекции — вес 1 (если оцениваются).

### 2.5. Дедлайны
- У каждого занятия (Activity) есть дедлайн. **По умолчанию дедлайн = дата следующего занятия у этой подгруппы** (для лабораторных) или следующей сессии той же группы (для лекций/практик).
- Дедлайн можно **выстраивать вручную** (переопределять) для каждого занятия или сессии.
- Просроченные работы отмечаются в UI (цветом / бейджем).

### 2.6. Статистика
- По студенту: средний балл, процент сданных занятий, разбивка по видам, динамика, место в рейтинге группы.
- По группе: средний балл, распределение, отстающие.
- По предмету: общая сводка.
- Mobile-first отображение (карточки, компактные графики).

### 2.7. Экспорт и импорт
- **JSON** — полный бэкап (предметы, студенты, занятия, сессии, оценки, посещаемость, настройки) с возможностью импорта.
- **Excel (.xlsx)** — для отчётов вне приложения.
- **Импорт из Excel не требуется**.

### 2.8. Аутентификация и безопасность
- **Supabase Auth** с кастомным OAuth-провайдером **Яндекс ID** (PKCE) для синхронизации между устройствами.
- **Локальный PIN-код** на входе с автоблокировкой после простоя (5 минут).
- **RLS** включён на каждой таблице: `auth.uid() = user_id`.
- **Криптошифрование локальной базы не используется** (осознанное решение).

### 2.9. Бэкап на Google Drive
- Автоматическая выгрузка данных в скрытую папку `appDataFolder` Google Диска через библиотеку **`drivestash`**.
- OAuth-авторизация через **Google Identity Services** со scope `https://www.googleapis.com/auth/drive.appdata` (отдельный поток от Яндекс-авторизации).
- Синхронизация при каждом изменении (фоновый push), с возможностью ручного вызова.
- Индикатор статуса синхронизации в UI (`idle | syncing | synced | offline | error`).
- DEFLATE-сжатие через `CompressionStream`.
- **Удаления**: только soft-delete (поле `deletedAt`).

### 2.10. Сессии занятий (ActivitySession)
- **Сессия** — это проведение занятия в конкретную дату.
- Для **лабораторных**: сессия привязана к подгруппе (`subgroupId` обязателен). Одно занятие может иметь несколько сессий (подгр. 1 — 12.03, подгр. 2 — 14.03).
- Для **лекций и практик**: сессия одна на всю группу (`subgroupId = null`).
- При создании занятия приложение предлагает даты сессий по умолчанию (чередование 1→2→1→2 для лабораторных; одна дата для лекций/практик). Любую дату можно переопределить.
- На экране предмета список занятий показывает суммарный статус по всем сессиям; детализация — внутри занятия.
- Внутри занятия — список сессий с датами и (для лабораторных) подгруппами.

## 3. Технические требования

### 3.1. Стек технологий

| Слой | Технология | Роль и обоснование |
| :--- | :--- | :--- |
| **Основа** | React 18 + Vite + TypeScript | Быстрая сборка, типизация, современный DX |
| **PWA** | `vite-plugin-pwa` | Service Worker, манифест, офлайн-кэш, установка на телефон |
| **Локальная БД** | **Dexie.js** (+ `dexie-react-hooks`) | Обёртка над IndexedDB. **Единственный источник истины для UI** |
| **Синхронизация (устройства)** | **Supabase** (`@supabase/supabase-js`) + кастомный OAuth **Яндекс ID** | Аутентификация и синхронизация между устройствами. RLS защищает данные на уровне строк |
| **Бэкап (Google Drive)** | **`drivestash`** | Бэкап в `appDataFolder` на Google Диске. **Авторизация — отдельный Google OAuth** (не Яндекс) |
| **Excel** | **SheetJS (`xlsx`)** | Экспорт в `.xlsx` для отчётов |
| **Стили** | **Tailwind CSS** | Mobile-first, две темы через `data-theme` и CSS-переменные |

> **Важно:** `drivestash` работает **только с Google Drive**. Авторизация в Supabase через Яндекс и бэкап на Google Drive — это **два независимых OAuth-потока**. Пользователь один раз подключает Google-аккаунт для бэкапа (кнопка в настройках).

### 3.2. Архитектура: Local-First + две синхронизации

**Слой данных:**
1. Все чтения/записи идут в **IndexedDB** (Dexie) — источник истины для UI.
2. Каждое изменение помечается как «ожидающее синхронизации» (mutation queue).

**Синхронизация между устройствами (Supabase) — основной канал:**
3. Фоновый движок: при появлении сети отправляет накопленные изменения в Supabase и забирает серверные обновления.
4. Стратегия разрешения конфликтов: last-write-wins по `updatedAt`.

**Бэкап на Google Drive (`drivestash`) — страховка, не замена Supabase:**
5. Каждый `put`/`delete` автоматически триггерит фоновый push в Drive.
6. OAuth-токен Google хранится локально, обновляется по необходимости.
7. **`drivestash` хранит все записи одного типа в одном JSON-файле** и при каждом push загружает/выгружает **весь файл целиком**. Разрешение конфликтов — Last-Write-Wins **на уровне всего файла**. Поэтому `drivestash` — **только страховка от потери IndexedDB**, не канал синхронизации между устройствами.
8. Имена storeName с префиксом проекта: `web-gradebook:subjects`, `web-gradebook:groups`, `web-gradebook:subgroups`, `web-gradebook:students`, `web-gradebook:enrollments`, `web-gradebook:activities`, `web-gradebook:sessions`, `web-gradebook:grades`, `web-gradebook:attendance`.

**Keep-alive для Supabase:**
9. Механизм, чтобы бесплатный проект Supabase не приостанавливался из-за недели простоя (лёгкий пинг через GitHub Actions или cron-сервис).

### 3.3. Развёртывание
- Хостинг: **GitHub Pages**, репозиторий `ezy4me/web-gradebook`.
- `base` в Vite: `/web-gradebook/`.
- Ключи Supabase — через переменные окружения (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`).
- **Яндекс OAuth Client ID** — через переменные окружения (`VITE_YANDEX_CLIENT_ID`). В Яндекс OAuth: Redirect URI — `https://ezy4me.github.io/web-gradebook/`, PKCE включён.
- **Google OAuth Client ID** — через переменные окружения (`VITE_GOOGLE_CLIENT_ID`). В Google Cloud Console: Authorized JavaScript origins — `https://ezy4me.github.io`, scope `drive.appdata`.
- Манифест PWA: `name: "web-gradebook"`, `start_url: "/web-gradebook/"`, `scope: "/web-gradebook/"`.

### 3.4. UI
- Две темы (тёмная/светлая) через CSS-переменные и `data-theme` на `<html>`.
- Переключение темы — кнопка в хедере и в настройках.
- Анимации переходов между экранами: `cubic-bezier(.2,0,0,1)`.
- Никаких эмодзи в UI, никакого глассморфизма и градиентов.
- Bottom navigation (4 вкладки), крупные тач-цели (≥44px).
- Индикатор синхронизации: зелёная/жёлтая точка на карточках и в хедере.
- Toast-уведомления.

6. **Синк-движки**: Supabase-синхронизация и `drivestash`-бэкап — очереди, триггеры, разрешение конфликтов, обработка ошибок.

## 5. Ограничения и допущения

- Основной сценарий — мобильный телефон.
- Интернет на паре может пропадать — приложение работает без него.
- Бесплатные тарифы Supabase, Google Drive API и GitHub Pages.
- Интерфейс — русский язык; две темы.
- `drivestash` хранит все записи одного типа в одном JSON-файле — подходит для сотен–низких тысяч записей. При каждом push грузится весь файл.
- Удаления — только через soft-delete (`deletedAt`) для **всех** сущностей.
- `drivestash` — **только бэкап**, не канал синхронизации между устройствами.
- Оценки привязаны к **сессии занятия**.
- Деление на подгруппы — **только для лабораторных**.
- Чередование подгрупп по умолчанию: `1 → 2 → 1 → 2…`; любая дата переопределяется вручную.
- **Авторизация в Supabase — через Яндекс ID**; бэкап на Google Drive — отдельный Google OAuth.
- **Криптошифрование локальной базы не используется**.
- **Импорт из Excel не требуется**.
- Роль «ассистент» не нужна.
- Посещаемость — обязательная сущность.

## 7. Порядок работы

1. Разработчик предоставляет **краткое резюме архитектуры**, **схему БД Supabase**, **схему Dexie**, **схему `drivestash`** и **потоки OAuth**.
2. Владелец подтверждает / корректирует.
3. Реализация **Этапа 1 (MVP)**.
4. По завершении каждого этапа — демонстрация и обратная связь.

**Предлагаемые этапы:**
- **Этап 1 (MVP):** локальное приложение (IndexedDB + Dexie), UI всех экранов, выставление баллов и посещаемости **по сессиям занятий**, дедлайны, статистика, экспорт/импорт JSON, PIN, две темы. Без Supabase и Google Drive.
- **Этап 2:** Supabase Auth (кастомный OAuth **Яндекс ID**) + RLS + синхронизация между устройствами.
- **Этап 3:** Google Drive бэкап через `drivestash` + отдельный Google OAuth.
- **Этап 4:** экспорт Excel, keep-alive Supabase, soft-delete, полировка UI.

**Статус в версии 0.9:** этапы 1–4 реализованы. Облачные этапы включаются ключами сборки
(см. [SETUP_CLOUD.md](SETUP_CLOUD.md)); без них приложение остаётся полностью офлайн.
